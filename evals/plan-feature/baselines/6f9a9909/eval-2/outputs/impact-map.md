# Repository Impact Map — TC-9002: Improve search experience

## Ambiguities Identified

The following ambiguities were identified in the feature description and require clarification from the product owner before implementation. Tasks below document assumptions where these gaps are filled in.

1. **"Search should be faster" — no performance targets specified.** The requirement states search is "currently too slow" but provides no baseline metrics (current response time) or target performance SLAs (e.g., p95 < 200ms). Without quantified targets, it is impossible to define a measurable acceptance criterion for "faster."

2. **"Results should be more relevant" — no relevance criteria defined.** The requirement states "users complain about irrelevant results" but does not define what constitutes a "relevant" result. There is no specification of ranking algorithm, field weighting, entity-type priority, or user-facing relevance indicators. The current search implementation (`SearchService` in `modules/search/src/service/mod.rs`) performs full-text search but the desired ranking behavior is unspecified.

3. **"Add filters" — filter specification missing.** The requirement says "some kind of filtering capability" without specifying: which fields should be filterable (entity type, severity, date range, license, etc.), what filter UI patterns to use (faceted search, dropdowns, free-text), whether filters should be combinable (AND/OR logic), or which entities the filters apply to (SBOMs, advisories, packages, or all).

4. **"Should be fast enough" — non-functional requirement without quantified targets.** The NFR "should be fast enough" is not measurable. No response time thresholds, throughput targets, or load testing criteria are provided.

5. **"Don't break existing functionality" — backward compatibility scope undefined.** No specification of what constitutes "existing functionality" — whether this means API contract stability (no breaking changes to `GET /api/v2/search` response shape), data consistency, or behavioral compatibility. No mention of API versioning strategy if the search endpoint response shape changes.
