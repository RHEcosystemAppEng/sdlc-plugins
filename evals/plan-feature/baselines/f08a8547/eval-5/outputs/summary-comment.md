## Architecture Summary

The plan replaces the `advisory_status` lookup table with a PostgreSQL `advisory_status_enum` column directly on the `advisory` table. This eliminates the join overhead that contributed ~40ms to advisory list endpoint p95 latency and simplifies the data model.

The change flows through four layers:
1. **Database** (Task 2) -- migration creates enum type, adds column, backfills data, drops FK and lookup table atomically
2. **ORM entities** (Task 3) -- SeaORM entity updated with `DeriveActiveEnum` enum type, advisory_status entity removed
3. **Service/API** (Task 4) -- advisory service queries and endpoint handlers use direct enum column access
4. **Ingestion** (Task 5) -- pipeline writes enum values directly instead of through lookup table

All changes are coordinated via a feature branch (`TC-9005`) to ensure atomicity -- the migration and code changes are tightly coupled and cannot be delivered independently to `main`.
