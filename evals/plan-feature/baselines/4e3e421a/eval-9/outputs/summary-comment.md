## Architecture summary
The verifier wrapper (`pre-verify.sh`) calls the gate (`resolve_gated_issue`). The gate searches the tracker through the client (`search_issues`), now authenticated with the service-account token through the gateway. The gate verifies only PRs whose linked issue is "Ready for Verification". Otherwise it skips with a log message.

**Fail-open risk handling:** the gateway answers unauthenticated or under-privileged requests with 200 + `[]`. That used to look like "no linked issue -> skip", so a run could finish green without verifying anything. The plan closes this in code at every layer:
- the client gets a positive auth check that does not trust a 2xx empty response (Task 1);
- the gate exits non-zero when auth can't be proven, before an empty result can count as a skip (Task 2);
- the wrapper fails on any non-zero gate exit, not only on 401/403 in stderr (Task 3).

Each layer has a fail-closed acceptance criterion and a test for the degraded path. The feature's "live run after merge" mitigation is kept as an extra check only. It is not the coverage.
