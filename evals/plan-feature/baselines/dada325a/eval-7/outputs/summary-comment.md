## Architecture summary
`ownerGroup` is added to the shared Service Catalog record in `src/catalog/store.py`.

Onboarding is not the only writer. The record is written by four workflows:
- registration (onboarding)
- scheduled sync
- fallback import
- on-demand refresh (`POST /api/catalog/refresh`)

It is read by the summary API and the downloadable report.

To meet the acceptance criteria ("after creation or update", "regardless of how that
record was populated"), the store gets one merge rule that every writer uses: keep the
existing `ownerGroup` unless a new non-empty value is supplied. Writes that would leave a
record without an `ownerGroup` are rejected (fail closed). Both readers expose the field,
and the export and fallback import formats match so the value survives the round trip.

The work stays in **one implementation task**, as the stakeholder asked for a small plan.
That task covers every writer and reader of the shared record, because a change to
onboarding alone would leave AC1 and AC2 unmet for sync, import and refresh. Workflow
mode is **direct-to-main**: no atomicity indicators apply across tasks.

## Scope note
The stakeholder sees this as an onboarding change, but the acceptance criteria cover the
shared record. The plan includes the scheduled sync, fallback import and on-demand
refresh paths, pending scope approval (see the impact map comment). If scope is limited
to onboarding, those paths and AC1/AC2 stay explicitly unresolved.

Open questions:
- Where `ownerGroup` comes from for records first created by non-registration paths.
- Whether existing records need a backfill.
