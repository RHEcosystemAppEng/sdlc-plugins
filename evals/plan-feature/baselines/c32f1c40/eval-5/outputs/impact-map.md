**Rationale:** Multiple atomicity indicators are present:

1. **Coordinated schema migration** — The database migration adds the `status` enum column and drops the `advisory_status` table and `status_id` FK column. Merging the migration without the code changes would break all advisory queries (they would still attempt to join the now-dropped `advisory_status` table). Merging the code changes without the migration would reference a `status` column that does not exist.

2. **Tightly coupled feature components** — The entity definitions (Task 3), service/endpoint queries (Task 4), and ingestion pipeline (Task 5) all depend on the schema change (Task 2). No individual task can be merged to `main` independently without breaking the application.

3. **Breaking internal API changes** — The SeaORM entity for `advisory` changes its field set (removing `status_id`, adding `status` enum). Any code referencing the old field would fail to compile after the entity update but before the consuming code is updated.

**Interdependent tasks:** Tasks 2 (migration), 3 (entities), 4 (service/endpoints), 5 (ingestion), and 6 (tests) are all interdependent. The migration must land with the code changes, and the code changes reference each other through the shared entity definitions.
