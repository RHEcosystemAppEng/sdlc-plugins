### Architecture summary
The pre-verify gate looks up the PR's linked tracker issue with the existing `search_issues` client. Verification runs only when that issue is "Ready for Verification". Other states, and a proven-authenticated "no linked issue" result, are skipped with a log message. Tracker calls move to the service-account token through the tracker API gateway.

**Fail-open risk handling:** the documented risk is that the gateway returns a successful empty search to unauthenticated or under-privileged requests. It is lowered into code-level, tested fail-closed behavior:
- `search_issues` raises and exits non-zero when an empty result cannot be proven authenticated (Task 1).
- `resolve_gated_issue` propagates that instead of skipping (Task 2).
- `scripts/pre-verify.sh` fails the run on that exit code instead of relying only on 401/403 stderr grepping (Task 2).

The suggested "live run after merge" is kept only as a supplementary post-merge check in Task 3. It is not the coverage for this risk.

Workflow mode: `direct-to-main`. Tasks are ordered so the gateway switch lands after the fail-closed guards.
