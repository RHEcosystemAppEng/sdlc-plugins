# Step 4 — Root Cause Analysis (ACME-520)

## Root cause determination

1. **What is broken:** `compute_risk_score()` returns `total_deps / vulnerable_deps` instead of `vulnerable_deps / total_deps`. Every risk assessment gets the reciprocal of its correct score, e.g. 20.0 instead of 0.05.
2. **Why it is broken:** the division operands are swapped. There is no guard for a zero denominator either, so `vulnerable_deps == 0` currently yields `+inf`. The only existing test uses `(10, 10)`, which gives 1.0 in either operand order, so the defect went undetected.
3. **Where it is broken:**
   - `modules/risk/src/score.rs::compute_risk_score`: the defect itself.
   - `modules/risk/src/assessment.rs::create_assessment`: persists the wrong value into `assessments.risk_score` at creation time.
   - `modules/risk/src/endpoints.rs::get_assessment`: serves the stored wrong value through `GET /api/v2/assessments/{id}`.
4. **How to verify the fix:** add a reproducer unit test asserting `compute_risk_score(100, 5) == 0.05`. Before the fix it fails, because the function returns 20.0. After the fix it passes. Add a migration check that seeded rows with inverted scores are corrected.

## Persistence impact
The wrong value is **persisted at ingestion time** to `assessments.risk_score` and is never recomputed on read. The code fix alone leaves all existing assessments wrong, so a data migration under `migration/` (Diesel convention) is required to correct historical rows.
