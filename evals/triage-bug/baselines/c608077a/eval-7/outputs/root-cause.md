# Step 4 — Root Cause Analysis (ACME-520)

## Root cause determination

1. **What is broken**: `compute_risk_score()` returns `total / vulnerable` instead of `vulnerable / total`. Every risk assessment therefore gets an inflated score; for example `20.0` instead of `0.05` for 5 of 100 vulnerable dependencies.
2. **Why it is broken**: the operands of the division are reversed, so the numerator and denominator are swapped. The existing unit test only covers `total == vulnerable` (`10, 10`), where operand order makes no difference, so the defect went undetected. Two related problems: with 0 vulnerable deps the buggy code returns `+inf`, and the corrected code would return `NaN` for 0 total deps unless guarded.
3. **Where it is broken**: `modules/risk/src/score.rs`, symbol `compute_risk_score`, in the line `total_deps as f64 / vulnerable_deps as f64`.
   - **Persistence impact:** `modules/risk/src/assessment.rs::create_assessment` writes the result into `assessments.risk_score` at assessment creation time (ingestion time). `modules/risk/src/endpoints.rs::get_assessment` (`GET /api/v2/assessments/{id}`) returns the stored value without recomputing it. A code fix alone leaves every existing assessment with a wrong score, so a **data migration is required**.
4. **How to verify the fix**: a reproducer unit test asserting `compute_risk_score(100, 5) == 0.05`. Before the fix it returns `20.0`. Add tests for the zero edge cases, plus a migration check that a pre-existing inflated row (e.g. `20.0`) becomes `0.05`.

### Root Cause

`compute_risk_score()` in the risk engine has its division operands reversed. It computes `total_deps / vulnerable_deps` instead of `vulnerable_deps / total_deps`, which inflates risk scores. For example, it returns `20.0` instead of `0.05` for an SBOM with 100 dependencies of which 5 are vulnerable. The existing unit test only covers `total == vulnerable`, where operand order does not matter, so the defect was never caught. The buggy code also returns `Infinity` when an SBOM has 0 vulnerable dependencies.

**Persistence impact:** the computed score is written to the `assessments.risk_score` column once, when the assessment is created, and `GET /api/v2/assessments/{id}` returns the stored value without recomputing it. Fixing the function only corrects new assessments. **Every existing assessment row holds an incorrect score and needs a data migration to correct it.**

### Affected Files

- `modules/risk/src/score.rs`, `compute_risk_score`: the defect (swapped operands)
- `modules/risk/src/assessment.rs`, `create_assessment`: persists the wrong value to `assessments.risk_score` (ingestion time)
- `modules/risk/src/endpoints.rs`, `get_assessment`: serves the persisted value as-is (not changed, but shows the impact)
- `modules/risk/tests/score_test.rs`: existing test does not cover `total != vulnerable`

### Suggested Approach

1. Fix `compute_risk_score` to return `vulnerable_deps / total_deps`, returning `0.0` when `total_deps == 0` (no NaN).
2. Add a Diesel data migration, `migration/<date>-000004_fix_assessment_risk_scores/`, that corrects existing `assessments.risk_score` values. Either recompute from SBOM source data, or invert the stored value (`1 / risk_score`, mapping `Infinity`/`NaN` to `0.0`) for rows with `risk_score > 1`. Ship it in the same deployment as the code fix.

### Reproducer Strategy

Add a unit test in `modules/risk/tests/score_test.rs` asserting `compute_risk_score(100, 5) == 0.05`. It fails before the fix (returns `20.0`) and passes after. Also add edge-case tests (`(100, 0) == 0.0`, `(0, 0) == 0.0`) and a migration test confirming that a seeded row with `risk_score = 20.0` becomes `0.05`.
