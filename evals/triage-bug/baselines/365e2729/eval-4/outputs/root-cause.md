## What is broken

`GET /api/v2/advisories` omits the `X-Total-Count` and `Link` pagination
headers when the date-range filter (`publishedAfter` / `publishedBefore`) is present.
The response body (the filtered page of advisories) is correct.

## Why it is broken

The pagination-header logic (run a total-count query, set `X-Total-Count`, build
`Link: <...>; rel="next"` when more pages exist) is applied only on the unfiltered
list path. When date-range parameters are supplied, the handler takes a different path
that returns only the result items. That may be a separate branch, query function, or
response type. This path never goes through the paginated/counted response wrapper.
Because both headers disappear together and the body stays correct, the likeliest
cause is that the whole wrapper is bypassed. A failure in a single header computation
is less likely.

A secondary possibility to rule out during implementation: the count query or `Link`
builder errors when filter predicates or extra query params are present, and the error
is silently swallowed. In that case the headers are dropped rather than the request
failing.

## Where it is broken

- **Repository:** acme-backend (Rust backend service)
- **Location:** the request handler for `GET /api/v2/advisories` and the service/query
  function it calls for date-range-filtered listing. The exact files and symbols were
  **not confirmed** (see investigation.md). Locate them by searching acme-backend
  for `X-Total-Count`, `rel="next"`, `publishedAfter` / `published_after`, and the
  advisories list handler.

## How to verify the fix (reproducer strategy)

Write an endpoint-level integration test in acme-backend's existing API test suite that:

1. Seeds more advisories in the date range than `limit` allows (e.g. 15 advisories
   published between 2025-01-01 and 2025-06-30, plus some outside the range).
2. Calls `GET /api/v2/advisories?publishedAfter=2025-01-01&publishedBefore=2025-06-30&limit=10`.
3. Asserts:
   - `X-Total-Count` is present and equals the number of **in-range** advisories (15),
     not the unfiltered total
   - `Link` is present and contains `rel="next"`, and the next URL keeps the
     `publishedAfter` / `publishedBefore` parameters
   - the body contains 10 advisories, all in range
4. Before the fix, the header assertions fail (headers absent). After the fix, they pass.
5. Control: the unfiltered request still returns correct headers.

**Root Cause**
The `GET /api/v2/advisories` handler sets the pagination headers (`X-Total-Count`,
`Link` with `rel="next"`) only on the unfiltered list path. When `publishedAfter` /
`publishedBefore` are supplied, the request takes a date-filtered path that returns the
correct items but skips the paginated/counted response wrapper, so both headers are
omitted. A secondary possibility is that the count query or `Link` builder silently
fails with filter params present.

**Affected Files**
- acme-backend: the advisories list handler for `GET /api/v2/advisories` and its
  date-range filtered query path. Exact file and symbol are to be confirmed. The
  available repository context did not include this code.

**Suggested Approach**
Route the date-filtered listing through the same pagination wrapper or helper used by
the unfiltered path. Compute the total count with the same filter predicates as the
items query. Build the `Link` next-page URL so it keeps all active query parameters,
including the date-range filters. Do not duplicate header logic.

`GET /api/v2/advisories?publishedAfter=2025-01-01&publishedBefore=2025-06-30&limit=10`, and
asserts that `X-Total-Count` equals the filtered total and that `Link` contains
`rel="next"` with the date params preserved. The test fails before the fix and passes after.
