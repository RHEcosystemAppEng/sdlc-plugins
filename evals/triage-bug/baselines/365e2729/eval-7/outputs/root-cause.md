# Step 4 — Root Cause Analysis: ACME-520

## Root cause determination

1. **What is broken** — `compute_risk_score()` returns `total_deps / vulnerable_deps`
   instead of `vulnerable_deps / total_deps`, so every risk score is the reciprocal of
   the correct value (e.g., 100 total / 5 vulnerable → `20.0` instead of `0.05`).
2. **Why it is broken** — the division operands are swapped (logic error). The only
   existing test (`test_risk_score_all_vulnerable`, `compute_risk_score(10, 10)`) uses
   equal inputs, for which operand order does not matter, so the defect was never caught.
3. **Where it is broken** — `modules/risk/src/score.rs::compute_risk_score`. The
   incorrect value is then persisted by `modules/risk/src/assessment.rs::create_assessment`
   into `assessments.risk_score` at creation time and served unchanged by
   `modules/risk/src/endpoints.rs::get_assessment`.
4. **How to verify the fix** — a unit test calling `compute_risk_score(100, 5)` must
   return `0.05` (fails today with `20.0`). A migration test/check must confirm existing
   rows are corrected (e.g., a row with `risk_score = 20.0` becomes `0.05`).

Single root cause (one swapped expression), manifesting across the compute and
persistence layers — **not** a decomposition trigger (Step 6). One Task is appropriate.

## Persistence impact

Persistence boundary found: `assessments.risk_score`, written once at ingestion time by
`create_assessment`. Existing records are stale and will not self-correct; the fix task
must include a Diesel data migration.
