# Step 4 -- Root Cause Analysis: ACME-511

## Root Cause Determination

### What is broken

The dark mode preference set via the Settings > Appearance panel is stored only in
ephemeral state (likely component state or sessionStorage). When the user closes the
browser and reopens it, this ephemeral state is destroyed and the application falls
back to the default theme (light mode). The preference persistence pipeline is
incomplete -- either the save-to-durable-storage step is missing, or the
restore-on-load step is missing, or both.

### Why it is broken

The dark mode toggle updates the current session's visual theme but does not persist
the user's choice to a durable storage mechanism. There are two requirements for
preference persistence across browser sessions:

1. **Write path**: When the user changes the preference, the new value must be
   written to durable storage (localStorage, a cookie, or a backend API/database).
2. **Read path**: When the application loads, it must read the stored preference and
   apply it before rendering the default theme.

At least one of these paths is missing or non-functional. The most likely scenario
is that the write path was never implemented -- the toggle only sets in-memory state
without calling `localStorage.setItem()` or a backend preferences endpoint.

### Where it is broken

The defect is in the frontend preference management layer:

- **Settings panel component** -- the dark mode toggle handler does not persist the
  preference to durable storage after updating the UI state
- **Application initialization** -- the theme initialization logic does not check
  for a previously stored preference before applying the default (light) theme

Potentially also:

- **Backend preferences API** -- if user preferences are intended to be stored
  server-side, the endpoint may not exist or may not handle the `theme`/`dark_mode`
  field

### How to verify the fix

A reproducer test should:

1. Simulate enabling dark mode through the settings interface
2. Simulate a browser session close and reopen (clear ephemeral state, reload)
3. Assert that after reload, the application renders in dark mode
4. Assert that the dark mode toggle shows the ON state

The test should fail before the fix (application reverts to light mode after reload)
and pass after the fix (application loads in dark mode after reload).

## Root Cause Comment (for Jira)

The following comment would be posted on ACME-511:

**Root Cause**: The dark mode preference is stored only in ephemeral state (component
state or sessionStorage) and is not written to durable storage (localStorage or
backend API). When the browser is closed, the ephemeral state is destroyed and the
application defaults to light mode on next load.

**Affected Files**: The Settings panel component (dark mode toggle handler) and the
application initialization/theme bootstrap logic.

**Suggested Approach**: Add a durable persistence layer for the dark mode preference.
When the toggle changes, write the preference to localStorage (and/or a backend
user preferences API). On application load, read the stored preference and apply it
before rendering. If a backend API is used, ensure the frontend reads the preference
on startup via an API call.

**Reproducer Strategy**: Write a test that toggles dark mode ON, simulates a browser
session restart (clears ephemeral state, reloads the page), and asserts that the
application still renders in dark mode with the toggle in the ON position.
