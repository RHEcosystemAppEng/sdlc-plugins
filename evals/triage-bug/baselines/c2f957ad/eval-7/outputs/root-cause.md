# Step 4 — Root Cause Analysis (ACME-520)

## Root cause determination

1. **What is broken** — `compute_risk_score()` returns the ratio of total to
   vulnerable dependencies instead of vulnerable to total. Every risk assessment is
   created with an inverted (and therefore inflated, for any SBOM with fewer
   vulnerable than total dependencies) `risk_score`.
2. **Why it is broken** — the division operands are swapped:
   `total_deps as f64 / vulnerable_deps as f64` should be
   `vulnerable_deps as f64 / total_deps as f64`. The only existing unit test uses
   equal inputs `(10, 10)`, for which both orders yield `1.0`, so the defect was
   never detected. The function also lacks a guard for a zero denominator.
3. **Where it is broken** —
   - Defect: `modules/risk/src/score.rs::compute_risk_score`
   - Persistence of the wrong value: `modules/risk/src/assessment.rs::create_assessment`
     (Diesel insert into `assessments.risk_score` at ingestion time)
   - Exposure: `modules/risk/src/endpoints.rs::get_assessment`
     (`GET /api/v2/assessments/{id}` returns the persisted value as-is)
4. **How to verify the fix** — a reproducer unit test in
   `modules/risk/tests/score_test.rs` calling `compute_risk_score(100, 5)` and
   asserting the result equals `0.05` (fails today with `20.0`, passes after the
   fix). A migration test/check verifies that existing `assessments` rows are
   corrected (e.g., a row holding `20.0` becomes `0.05`).

## Persistence impact

The buggy value is persisted at ingestion time to `assessments.risk_score` and is
never recomputed on read. A code-only fix leaves every existing assessment with a
wrong score, so the fix task must include a Diesel data migration
(`migration/<YYYY-MM-DD>-000004_fix_inverted_risk_scores/`) that corrects existing rows.

## Decomposition Guard (Step 6)

Single root cause (swapped operands in one function). The migration is a direct
consequence of the same defect, not an independent issue. **No decomposition
needed** — one Task is appropriate.

> **Root Cause**
>
> `compute_risk_score()` in `modules/risk/src/score.rs` divides `total_deps` by
> `vulnerable_deps` instead of `vulnerable_deps` by `total_deps`. For an SBOM with
> 100 dependencies of which 5 are vulnerable, it returns `20.0` instead of `0.05`.
> The existing unit test only covers `total == vulnerable`, which hides the swap.
>
> The computed score is persisted once, at assessment creation time, into
> `assessments.risk_score` by `create_assessment()` and is returned unchanged by
> `GET /api/v2/assessments/{id}`. Fixing the function alone therefore will not
> correct existing assessments — they remain stale.
>
> **Affected Files**
>
> - `modules/risk/src/score.rs` — `compute_risk_score` (defect)
> - `modules/risk/src/assessment.rs` — `create_assessment` (persists the wrong value to `assessments.risk_score`)
> - `modules/risk/src/endpoints.rs` — `get_assessment` (serves the persisted value)
> - `modules/risk/tests/score_test.rs` — insufficient coverage (`(10, 10)` only)
>
> **Suggested Approach**
>
> - Swap the operands in `compute_risk_score` so it returns `vulnerable / total`,
>   and guard against `total_deps == 0` (return `0.0`).
> - Add a Diesel data migration under `migration/` (following the
>   `YYYY-MM-DD-NNNNNN_description/up.sql|down.sql` convention) that corrects
>   existing `assessments.risk_score` values — recompute from source SBOM data if
>   available, otherwise invert the stored value (`1.0 / risk_score`, mapping
>   `Infinity`/`NaN` to `0.0`).
>
> **Reproducer Strategy**
>
> Add a unit test in `modules/risk/tests/score_test.rs` asserting
> `compute_risk_score(100, 5) == 0.05`. It fails today (returns `20.0`) and passes
> after the fix. Add a zero-total edge case test and verify the migration corrects
> a seeded row holding `20.0` to `0.05`.
