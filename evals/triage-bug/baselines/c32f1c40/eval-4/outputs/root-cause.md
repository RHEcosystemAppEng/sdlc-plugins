# Step 4 -- Root Cause Analysis: ACME-510

## Root Cause Determination

### What is broken

The `/api/v2/advisories` endpoint does not return pagination headers (`X-Total-Count`
and `Link`) when the request includes date range filter parameters (`publishedAfter`
and `publishedBefore`). The response body contains correct filtered results, but
clients cannot determine total pages or navigate to subsequent pages.

### Why it is broken

The filtered query path for the advisories endpoint bypasses the pagination header
generation logic. When date range parameters are applied, the endpoint uses a
different query execution path that returns filtered results without computing the
total count needed for `X-Total-Count` or constructing the `Link` header. The
unfiltered path correctly invokes pagination header generation, confirming that the
pagination logic itself works -- it is simply not called in the filtered code path.

### Where it is broken

Based on the investigation, the defect is in the advisories endpoint handler within
the acme-backend repository. The specific location is the query handler for
`/api/v2/advisories` that processes `publishedAfter` and `publishedBefore` parameters.
The filtered query branch does not invoke the same pagination header computation that
the unfiltered branch uses.

### How to verify the fix

A reproducer test should:

1. Set up a mock advisory dataset with a known number of entries.
2. Call `GET /api/v2/advisories?publishedAfter=2025-01-01&publishedBefore=2025-06-30&limit=10`.
3. Assert that the response includes the `X-Total-Count` header with the correct total.
4. Assert that the response includes the `Link` header with a `rel="next"` entry when
   more pages exist.
5. Verify that the response body still contains the correct filtered advisories.
