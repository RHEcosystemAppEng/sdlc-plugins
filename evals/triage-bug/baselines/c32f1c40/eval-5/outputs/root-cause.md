# Step 4 -- Root Cause Analysis: ACME-511

## Root Cause Determination

### What is broken

The dark mode preference selected by the user in the Settings > Appearance panel is not
persisted across browser sessions. When the user enables dark mode and then closes and
reopens the browser, the application reverts to light mode with the toggle reset to OFF.

### Why it is broken

The dark mode toggle state is held only in application runtime state (e.g., component
state or an in-memory store) and is not written to a durable client-side storage mechanism
(such as `localStorage`, `sessionStorage`, or a cookie). When the browser is closed, the
in-memory state is lost and the application initializes with the default theme (light mode).

Additionally, the convention heading extraction logic in the plan-feature skill has a
trailing whitespace bug: `line[3:]` does not strip trailing whitespace from `## ` headings
in CONVENTIONS.md, causing exact-match comparisons to fail. While this is a separate code
quality issue discovered during investigation, it does not directly cause the dark mode
persistence bug.

### Where it is broken

- **Primary defect**: The Settings > Appearance component (or its associated state
  management code) that handles the dark mode toggle. The toggle handler updates runtime
  state but does not write the preference to persistent storage.
- **Secondary observation**: `plugins/sdlc-workflow/skills/plan-feature/SKILL.md` --
  the convention heading extraction at `line[3:]` has a trailing whitespace issue that
  affects convention-aware task enrichment.

### How to verify the fix

A reproducer test should:

1. Simulate enabling dark mode via the settings panel
2. Simulate a browser session close and reopen (clear runtime state while preserving
   persistent storage)
3. Assert that the application loads in dark mode after the simulated restart
4. Assert that the dark mode toggle shows as ON
