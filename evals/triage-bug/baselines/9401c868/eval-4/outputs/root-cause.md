# Step 4 -- Root Cause Analysis

## Root Cause Determination

### What is broken

The `GET /api/v2/advisories` endpoint does not return `X-Total-Count` and `Link`
pagination headers when the request includes date-range filter parameters
(`publishedAfter`, `publishedBefore`). The response body contains the correct
filtered advisory data, but clients cannot determine total pages or navigate
between pages.

### Why it is broken

The endpoint handler has two divergent query paths: an unfiltered path that
invokes the shared pagination header utility (count query + header generation),
and a date-range filtered path that bypasses the pagination utility entirely.
When the filtered path was implemented, the pagination header logic was not
carried over or integrated into the filtered code branch.

### Where it is broken

- **Primary file:** `src/api/v2/advisories.rs` -- the endpoint handler where the
  filtered query path diverges from the unfiltered path
- **Pagination utility:** `src/api/pagination.rs` (or equivalent) -- the shared
  utility that generates `X-Total-Count` and `Link` headers. This module is
  functioning correctly; the problem is that the filtered path does not call it.

### How to verify the fix

A reproducer test should:
1. Send `GET /api/v2/advisories?publishedAfter=2025-01-01&publishedBefore=2025-06-30&limit=10`
2. Assert that the response includes the `X-Total-Count` header with a value matching
   the number of advisories in the filtered date range
3. Assert that the response includes a `Link` header with `rel="next"` when more
   pages exist beyond the limit
4. Verify that the response body still contains the correct filtered results
