# Step 4 -- Root Cause Analysis: ACME-510

## Root Cause Determination

### What is broken

The `/api/v2/advisories` endpoint does not include `X-Total-Count` and `Link` pagination headers in the response when the request contains date range filter query parameters (`publishedAfter` and `publishedBefore`). The response body correctly returns filtered advisory results, but clients cannot determine total result count or navigate pages.

### Why it is broken

The pagination header generation logic is conditional on the query path taken. When date range filter parameters are present, the code follows a filtered query branch that either:

1. Skips the total count query needed to compute `X-Total-Count`, or
2. Executes the count query without applying the date range filter conditions, producing an incorrect count that is then suppressed, or
3. Bypasses the header-setting step entirely due to a missing or incorrect conditional check.

The unfiltered query path correctly includes the count query and header generation, which is why non-filtered requests work as expected. The defect is the asymmetry between the filtered and unfiltered code paths in how they handle pagination header generation.

### Where it is broken

- **Advisory endpoint handler** -- the route handler for `GET /api/v2/advisories` in the acme-backend repository
- **Pagination header generation** -- the logic that computes the total count and constructs `X-Total-Count` and `Link` headers
- **Date range filter branch** -- the conditional path that applies `publishedAfter`/`publishedBefore` parameters to the query

### How to verify the fix

A reproducer test should:

1. Set up test advisory data with known dates spanning a date range
2. Call `GET /api/v2/advisories?publishedAfter=<date1>&publishedBefore=<date2>&limit=<n>` where the total filtered results exceed the limit
3. Assert that the response includes:
   - `X-Total-Count` header with the correct total count of filtered advisories
   - `Link` header with `rel="next"` when more pages exist
4. Also verify that the response body still contains the correct filtered results (no regression)
5. Compare behavior with a non-filtered request to confirm existing pagination still works
