# Step 4 — Root Cause Analysis (ACME-520)

## Root cause determination

1. **What is broken** — `compute_risk_score()` returns the inverse of the intended ratio.
   For 100 total / 5 vulnerable dependencies it returns `20.0` instead of `0.05`.
2. **Why it is broken** — the division operands are swapped: the function computes
   `total_deps as f64 / vulnerable_deps as f64` instead of
   `vulnerable_deps as f64 / total_deps as f64`. The only existing unit test
   (`test_risk_score_all_vulnerable`, `compute_risk_score(10, 10) == 1.0`) uses equal
   inputs, so it is insensitive to operand order and never caught the defect.
3. **Where it is broken** — `modules/risk/src/score.rs::compute_risk_score` (acme-backend).
   The wrong value propagates through `modules/risk/src/assessment.rs::create_assessment`,
   which **persists** it to `assessments.risk_score` at creation time, and is served
   verbatim by `modules/risk/src/endpoints.rs::get_assessment`.
4. **How to verify the fix** — a reproducer unit test asserting
   `compute_risk_score(100, 5) == 0.05` (fails today with `20.0`, passes after the fix),
   plus a migration test/check that pre-existing `assessments` rows are corrected.

## Persistence impact

The buggy output is written to the database at ingestion time (`assessments.risk_score`)
and never recomputed on read. Fixing the function alone corrects only future
assessments; all existing assessments retain inflated scores. A Diesel data migration
under `migration/` is required to correct existing rows.

## Decomposition Guard (Step 6) check

Single root cause (swapped operands) manifesting through one write path; the data
migration is a direct consequence of the same defect. **Not** a decomposition
trigger — a single Task is appropriate.

**Root Cause**
`compute_risk_score()` in `modules/risk/src/score.rs` has its division operands swapped:
it computes `total_deps / vulnerable_deps` instead of `vulnerable_deps / total_deps`,
inverting every risk score (e.g. 100 total / 5 vulnerable → `20.0` instead of `0.05`).
The existing test `test_risk_score_all_vulnerable` uses equal inputs (10, 10) and cannot
detect operand order. The score is persisted to `assessments.risk_score` by
`create_assessment()` at creation time and returned as-is by `GET /api/v2/assessments/{id}`,
so **all existing assessments contain incorrect scores**.

**Affected Files**
- `modules/risk/src/score.rs` — `compute_risk_score` (defect)
- `modules/risk/src/assessment.rs` — `create_assessment` (persists the wrong value to `assessments.risk_score`)
- `modules/risk/src/endpoints.rs` — `get_assessment` (serves the persisted value; no change needed)

**Suggested Approach**
- Swap the operands in `compute_risk_score` and define behavior for `total_deps == 0`
  (return `0.0` instead of producing NaN).
- Add a Diesel data migration (`migration/YYYY-MM-DD-000004_fix_assessment_risk_scores/`)
  that corrects existing `assessments.risk_score` values (recompute from source
  dependency counts if available; otherwise take the reciprocal of the stored value,
  mapping `inf` → `0.0`).

**Reproducer Strategy**
Add a unit test in `modules/risk/tests/score_test.rs` asserting
`compute_risk_score(100, 5)` ≈ `0.05`. It fails today (returns `20.0`) and passes after
the fix. Additionally verify that an assessment row inserted with the old (inverted)
value is corrected after running the migration.
