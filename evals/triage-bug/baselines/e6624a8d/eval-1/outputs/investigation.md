# Steps 2-3 -- Codebase Investigation Findings

## Step 2 -- Reproduce/Trace

### Reproduction method: Code-path tracing

The bug involves the plan-feature skill's convention parsing logic, which is a skill
invocation rather than a directly runnable command. Code-path tracing was used instead
of direct reproduction.

### Trace: Convention heading extraction

**Entry point**: `/plan-feature ACME-100` skill invocation

**Code path traced** (from `plugins/sdlc-workflow/skills/plan-feature/SKILL.md`):

1. The skill reads `CONVENTIONS.md` and splits it into lines.
2. For each line starting with `## `, it extracts the heading text using `line[3:]`.
3. The extracted section name is stored as a dictionary key in `conventions[section_name]`.

**Defect location**: The extraction at `line[3:]` does NOT strip trailing whitespace.

When the heading line is `## Migration Patterns  \n`, the extraction produces
`"Migration Patterns  "` (with two trailing spaces) as the dictionary key.

### Trace: Convention matching

**Code path traced** (from convention-aware task enrichment):

```python
if convention_name in discovered_conventions:
    notes.append(f"Per CONVENTIONS.md {convention_name}: {action}")
```

The match lookup uses `convention_name` (e.g., `"Migration Patterns"`) as the key,
but the dictionary contains `"Migration Patterns  "` (with trailing spaces). The
exact-match comparison fails silently -- no KeyError is raised because `in` simply
returns `False`, and no warning is logged.

### Trace conclusion

The bug is **confirmed by trace**. The divergence between expected and actual behavior
occurs at the heading extraction step (`line[3:]`), which propagates trailing whitespace
into the dictionary key, causing all downstream exact-match lookups to fail.

### Persistence-impact analysis

The buggy function's output (the extracted convention section names) is used to
generate task description text, which is posted to Jira via the API. This is a
skill output rendered into a Jira issue description -- it is not persisted to a
local database.

**Conclusion**: No persistence boundary found. The output is computed at invocation
time and written to Jira as part of the task description. No data migration is needed.
Fixing the heading extraction logic will correct all future invocations. Previously
created tasks with missing conventions would need to be regenerated by re-running
`/plan-feature`, but this is an operational concern, not a data migration.
