# Step 4 — Root Cause Analysis: ACME-520

## Root cause determination

1. **What is broken**: `compute_risk_score()` returns the inverse of the intended ratio. It computes
   `total_deps / vulnerable_deps` when it should compute `vulnerable_deps / total_deps`.
2. **Why it is broken**: the division operands in
   `modules/risk/src/score.rs::compute_risk_score` are swapped. The only existing unit test
   (`test_risk_score_all_vulnerable`, which uses `10, 10`) gives the same result in either operand
   order, so the defect was never caught. The function also has no zero-denominator guard.
3. **Where it is broken**:
   - Defect: `modules/risk/src/score.rs::compute_risk_score`
   - Persistence of the wrong value: `modules/risk/src/assessment.rs::create_assessment`, which
     inserts into `assessments.risk_score` at creation time
   - Exposure: `modules/risk/src/endpoints.rs::get_assessment` (`GET /api/v2/assessments/{id}`),
     which returns the stored value without recomputing it
4. **How to verify the fix**: a reproducer test calling `compute_risk_score(100, 5)` must return
   `0.05`. Before the fix it returns `20.0`, so the test fails. A migration check must confirm that
   existing `assessments` rows are corrected (for example, a stored `20.0` becomes `0.05`).

**Persistence impact**: YES. The wrong value is persisted at ingestion time in
`assessments.risk_score` and is never recomputed. A code fix alone leaves every historical
assessment wrong, so a Diesel data migration under `migration/` is needed.

**Decomposition Guard (Step 6)**: single root cause (swapped operands). The code fix and the data
migration both fix the same defect and its consequence, so one Task is appropriate and no split
prompt is needed.

## Simulated Jira comment on ACME-520 (`jira.add_comment`, ADF contentFormat)

**Root Cause**

`compute_risk_score()` in `modules/risk/src/score.rs` divides `total_deps` by `vulnerable_deps`
instead of `vulnerable_deps` by `total_deps`. The operands are swapped, so every risk score is
the reciprocal of the correct value (for example, 100 total / 5 vulnerable gives `20.0` instead of
`0.05`). The existing test `test_risk_score_all_vulnerable` uses equal inputs (10, 10), so it
cannot detect the swap.

The wrong score is **persisted**. `create_assessment()` in `modules/risk/src/assessment.rs`
writes it to `assessments.risk_score` when the assessment is created, and `get_assessment()`
(`GET /api/v2/assessments/{id}`) returns the stored value without recomputing it. All existing
assessments therefore hold wrong scores.

**Affected Files**

- `modules/risk/src/score.rs`, `compute_risk_score`: defect (swapped operands, no zero guard)
- `modules/risk/src/assessment.rs`, `create_assessment`: persists the wrong value to `assessments.risk_score`
- `modules/risk/src/endpoints.rs`, `get_assessment`: serves the persisted wrong value
- `modules/risk/tests/score_test.rs`: missing coverage for `total != vulnerable`

**Suggested Approach**

1. Swap the operands in `compute_risk_score` to `vulnerable_deps / total_deps`, and return `0.0`
   when `total_deps == 0`.
2. Add a Diesel data migration (`migration/YYYY-MM-DD-000004_fix_assessment_risk_score/`) that
   corrects existing `assessments.risk_score` rows. Recompute from source data, or take the
   reciprocal of the stored value, with Infinity/NaN mapped to `0.0`.

**Reproducer Strategy**

Add a test in `modules/risk/tests/score_test.rs` asserting `compute_risk_score(100, 5) == 0.05`.
It fails before the fix (returns `20.0`) and passes after. Also verify that the migration turns a
stored `20.0` into `0.05`.
