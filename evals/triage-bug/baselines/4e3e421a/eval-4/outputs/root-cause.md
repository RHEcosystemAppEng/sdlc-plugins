## What is broken
`GET /api/v2/advisories` leaves out the `X-Total-Count` and `Link` (`rel="next"`) response headers when the request has date-range filters (`publishedAfter` / `publishedBefore`). The response body (the filtered advisories) is correct.

## Why it is broken
The date-filtered request takes a different code path from the unfiltered one, and that path does not produce pagination metadata. One of these is the likely cause:
1. The filtered branch builds its response straight from the result rows and skips the shared pagination response wrapper/helper that the unfiltered branch uses to emit `X-Total-Count` and `Link`. **Most likely.**
2. The filtered branch skips the total-count query (or does not pass the filter predicates to it). The pagination helper then has no total and emits no headers.

In both cases, filtering is not wired into the shared pagination flow.

## Where it is broken
- Repository: **acme-backend** (`/home/dev/repos/acme-backend`)
- Location: the `/api/v2/advisories` list handler's date-filter branch, and/or the advisory list query function's count path.
- **File paths are unconfirmed.** They were not in the supplied context. Locate them with Grep for `publishedAfter|published_after`, `X-Total-Count|x-total-count`, and the `/api/v2/advisories` route registration.

## How to verify the fix
A reproducer integration test that:
1. Seeds more advisories than `limit` inside the date range (e.g., 15 with `published` dates between 2025-01-01 and 2025-06-30), plus some outside it.
2. Calls `GET /api/v2/advisories?publishedAfter=2025-01-01&publishedBefore=2025-06-30&limit=10`.
3. Asserts that `X-Total-Count` is present and equals the number of in-range advisories (15, not the total table size).
4. Asserts that a `Link` header is present and contains `rel="next"`, and that the next URL **keeps** the `publishedAfter`/`publishedBefore` parameters.
5. Before the fix it fails (headers missing). After the fix it passes.
