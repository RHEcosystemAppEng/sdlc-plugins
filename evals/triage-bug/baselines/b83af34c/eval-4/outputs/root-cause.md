# Step 4 -- Root Cause Analysis

## Root Cause Determination

### What is broken

The `/api/v2/advisories` endpoint handler has two distinct code paths for building
query results: one for unfiltered requests and one for date-range-filtered requests
(when `publishedAfter`/`publishedBefore` query parameters are present). The filtered
code path does not invoke the pagination header generation logic, causing the
`X-Total-Count` and `Link` headers to be absent from filtered responses.

### Why it is broken

When the date range filtering was implemented, the filtered query path was added as a
separate branch that constructs and returns the filtered result set directly, without
routing through the pagination header utility (`build_pagination_headers`). The
unfiltered path correctly calls this utility, but the filtered path bypasses it. This
is a missing integration -- the pagination header logic was not wired into the new
filtered code path.

### Where it is broken

- **API endpoint handler**: the advisories endpoint handler file (e.g.,
  `src/api/v2/advisories.rs` or equivalent) -- the branch handling date-range
  filters does not call the pagination header builder.
- **Pagination utility**: `build_pagination_headers()` (or equivalent) -- the
  function itself is correct but is simply not called from the filtered path.

### How to verify the fix

A reproducer test should:
1. Call `GET /api/v2/advisories?publishedAfter=2025-01-01&publishedBefore=2025-06-30&limit=10`
2. Assert that the response includes the `X-Total-Count` header with the correct
   count of matching advisories
3. Assert that the response includes the `Link` header with `rel="next"` when more
   pages exist
4. Verify that the response body still contains correctly filtered results

The test should fail before the fix (demonstrating the bug) and pass after the fix.
