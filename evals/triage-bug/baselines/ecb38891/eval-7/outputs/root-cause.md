## Root Cause

The `compute_risk_score()` function in `modules/risk/src/score.rs` has its division operands
reversed. It computes `total_deps as f64 / vulnerable_deps as f64` instead of the correct
`vulnerable_deps as f64 / total_deps as f64`. For an SBOM with 100 total dependencies and
5 vulnerable ones, this produces a risk score of `20.0` instead of the correct `0.05`.

Additionally, the incorrect score is persisted to the `assessments` table (`risk_score`
column) at ingestion time by `create_assessment()` in `modules/risk/src/assessment.rs`.
The `GET /api/v2/assessments/{id}` endpoint reads the persisted value directly from the
database without recomputing it. This means all existing assessments contain inflated risk
scores that will not self-correct when the code is fixed. A data migration is required to
recompute existing records.

## Affected Files

- `modules/risk/src/score.rs` -- `compute_risk_score()` function: division operands
  `total_deps / vulnerable_deps` are swapped (should be `vulnerable_deps / total_deps`)
- `modules/risk/src/assessment.rs` -- `create_assessment()` function: persists the
  incorrect score to `assessments::risk_score` at ingestion time
- `modules/risk/src/endpoints.rs` -- `get_assessment()` function: reads the persisted
  score without recomputing, serving stale incorrect values

## Suggested Approach

1. **Code fix**: Swap the division operands in `compute_risk_score()`:
   ```rust
   vulnerable_deps as f64 / total_deps as f64
   ```

2. **Data migration**: Create a Diesel migration to recompute `risk_score` for all existing
   assessments by joining with the source SBOM data to obtain `total_deps` and
   `vulnerable_deps`, then updating the column with the correct ratio.

## Reproducer Strategy

Add a test in `modules/risk/tests/score_test.rs` that calls `compute_risk_score()` with
unequal arguments (e.g., `total_deps=100, vulnerable_deps=5`) and asserts the result is
`0.05`. This test should fail before the fix (returns `20.0`) and pass after the fix
(returns `0.05`). The existing `test_risk_score_all_vulnerable` test with equal arguments
(10, 10) masks the bug because `10/10 = 1.0` regardless of operand order.
