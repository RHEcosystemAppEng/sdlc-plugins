# Step 4 — Root Cause Analysis (ACME-520)

## Root cause determination

1. **What is broken** — Risk scores for SBOM assessments are inverted: the function
   returns `total / vulnerable` instead of `vulnerable / total`, so scores are inflated
   (e.g., `20.0` instead of `0.05`). Because the score is persisted at creation time,
   every existing assessment in the database also holds the wrong value.
2. **Why it is broken** — The division operands in `compute_risk_score()` are swapped
   (`total_deps as f64 / vulnerable_deps as f64`). The only existing unit test uses
   equal operands (`compute_risk_score(10, 10) == 1.0`), so the swap was never caught.
3. **Where it is broken**
   - Defect: `modules/risk/src/score.rs::compute_risk_score`
   - Persistence of the bad value: `modules/risk/src/assessment.rs::create_assessment`
     -> `assessments.risk_score` (written once, at ingestion time)
   - Exposure: `modules/risk/src/endpoints.rs::get_assessment` returns the stored value
     without recomputation
4. **How to verify the fix** — A unit test calling `compute_risk_score(100, 5)` must
   assert `0.05` (it returns `20.0` today). A migration test/verification must show
   that a pre-existing `assessments` row with `risk_score = 20.0` becomes `0.05`.

This is a single root cause (one swapped expression) with a downstream data-correction
consequence — **not** a Decomposition Guard trigger (Step 6). A single Task covering
the code fix plus the data migration is appropriate.

**Root Cause**

`compute_risk_score()` in `modules/risk/src/score.rs` divides with the operands swapped:
it computes `total_deps / vulnerable_deps` instead of `vulnerable_deps / total_deps`.
For an SBOM with 100 dependencies and 5 vulnerable, it returns `20.0` instead of `0.05`.
The only existing test (`test_risk_score_all_vulnerable`, `compute_risk_score(10, 10)`)
uses equal operands, so it passes regardless of operand order.

**Persistence impact:** the score is written to `assessments.risk_score` once, when the
assessment is created (`create_assessment` in `modules/risk/src/assessment.rs`), and
`GET /api/v2/assessments/{id}` returns the stored value without recomputing it. Fixing
the function alone corrects only new assessments; all existing assessments keep the
inflated score until a data migration corrects them.

**Affected Files**

- `modules/risk/src/score.rs` — `compute_risk_score` (defect)
- `modules/risk/src/assessment.rs` — `create_assessment` (persists the bad value to `assessments.risk_score`)
- `modules/risk/src/endpoints.rs` — `get_assessment` (returns persisted value as-is; no change needed)
- `modules/risk/tests/score_test.rs` — missing coverage for `total != vulnerable`

**Suggested Approach**

- Swap the operands in `compute_risk_score` to `vulnerable_deps / total_deps`, and
  define behavior for `total_deps == 0` (return `0.0`) to avoid NaN/Infinity.
- Add a Diesel data migration under `migration/` (next sequence `000004`, following the
  `YYYY-MM-DD-NNNNNN_description/up.sql|down.sql` convention) that corrects existing
  `assessments.risk_score` values — recompute from source counts if available, otherwise
  replace each stored value with its reciprocal (`Infinity`/`NaN` -> `0.0`).

**Reproducer Strategy**

- Unit test in `modules/risk/tests/score_test.rs`: `compute_risk_score(100, 5)` must
  equal `0.05` (fails today with `20.0`, passes after the fix). Add an asymmetric case
  in the opposite direction and a `total_deps == 0` case.
- Migration verification: seed an `assessments` row with `risk_score = 20.0`, run the
  migration, assert `risk_score = 0.05`.
