# Step 4 – Root Cause Analysis (ACME-511)

## Root cause determination

### 1. What is broken

The user's dark-mode preference does not survive a full browser restart. After a restart
the app falls back to the default theme (light), and the Settings > Appearance toggle
shows OFF.

### 2. Why it is broken (likely, not confirmed in code)

The theme preference is either **not written to durable storage** or **not read back and
applied when the app starts**. Candidate causes, most likely first:

1. The preference is held only in in-memory UI state or in `sessionStorage`. Both are
   cleared when the browser closes.
2. The preference is persisted (for example to `localStorage` or a user-preferences API),
   but the theme initializer ignores it and always starts from a hard-coded `light`
   default, or applies the stored value and then overwrites it with the default.
3. A backend user-preferences endpoint exists, but the toggle never calls it, or the app
   never fetches it on load.

All three have the same root cause class: **the dark-mode preference is not round-tripped
through persistent storage.** This is a single defect, so the Decomposition Guard is not
triggered.

### 4. How to verify the fix

A reproducer test should:
1. Set the dark-mode preference to ON through the same code path the toggle uses.
2. Simulate a new browser session: clear in-memory state and `sessionStorage`, then
   re-initialize the app or theme provider while keeping durable storage (`localStorage`,
   cookies, or the backend preference record).
3. Assert that the active theme is `dark` and the toggle is ON.
   - Before the fix, it fails (theme is `light`, toggle OFF, matching the Actual Result).
   - After the fix, it passes (matching the Expected Result).

## Persistence impact
