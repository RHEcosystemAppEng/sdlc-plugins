# Step 4 — Root Cause Analysis: ACME-520

## Root cause determination

1. **What is broken** — `compute_risk_score()` returns `total_deps / vulnerable_deps` instead of `vulnerable_deps / total_deps`. Every risk assessment receives an inverted, inflated score (e.g., 20.0 instead of 0.05 for 5 vulnerable out of 100).
2. **Why it is broken** — The division operands are swapped (logic error). It went undetected because the only existing test (`test_risk_score_all_vulnerable`, `compute_risk_score(10, 10)`) uses equal inputs, where operand order does not matter. Secondary: the division has no guard for zero denominators (`vulnerable_deps == 0` currently yields `+Infinity`).
3. **Where it is broken**
   - Defect: `modules/risk/src/score.rs::compute_risk_score`
   - Persisted by: `modules/risk/src/assessment.rs::create_assessment` → `assessments.risk_score` (written once at creation time)
   - Exposed by: `modules/risk/src/endpoints.rs::get_assessment` (`GET /api/v2/assessments/{id}`), which returns the stored value without recomputation
4. **How to verify the fix** — A unit test calling `compute_risk_score(100, 5)` must assert `0.05` (it returns `20.0` before the fix). Plus a migration check: an `assessments` row seeded with `risk_score = 20.0` must read `0.05` after the migration runs.

**Persistence impact:** Yes. Incorrect values have already been written to `assessments.risk_score` at ingestion time and are never recomputed. A code fix alone leaves all historical assessments wrong; a data migration is required.
