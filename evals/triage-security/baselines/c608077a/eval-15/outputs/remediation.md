## Step 8 decision

The issue is **scoped** to 2.2.x and other streams are affected, so **Case A followed by Case B** applies.

- Affected: RHTPA 2.2.0, 2.2.1, 2.2.2 (quinn-proto 0.11.9 / 0.11.12).
- Already remediated: RHTPA 2.2.3 and 2.2.4 ship quinn-proto 0.11.14. The current release-repo pin
  (`v0.4.12`) is not vulnerable, and `release/0.4.z` tags since `v0.4.11` carry the fix.
- A dependency bump plus downstream propagation pair would make no change, because the latest 2.2.x
  build already ships 0.11.14.
- Recommendation: keep TC-8001 open with the corrected Affects Versions and set fixVersion
  **RHTPA 2.2.3** (the first fixed release). Then move it through the normal fixed-in-release
  workflow, with the customer remedy being "upgrade to 2.2.3 or later".
- If the engineer still wants standard Case B tasks for 2.2.x, the 2-task Cargo "dependency bump"
  variant would apply: target `release/0.4.z` in `rhtpa-backend`, plus downstream propagation in
  `rhtpa-release.0.4.z`, linked Depend -> TC-8001 and Blocks between them. Note that the upstream
  branch HEAD was not inspected.
