## Decision

- Supported versions are affected (2.1.0, 2.1.1, 2.2.0, 2.2.1, 2.2.2), so **Case C (close as Not a Bug) does not apply**.
- The issue is scoped to `[rhtpa-2.2]` and another stream (2.1.x) is affected, so **Case A (cross-stream impact)** applies, followed by Case B.
- Ecosystem is Cargo, a source dependency, so each stream that needs a fix gets **2 tasks**.

### In-scope stream 2.2.x (Case B)

The affected versions are 2.2.0, 2.2.1 and 2.2.2. The fix (quinn-proto 0.11.14) has **already shipped** in 2.2.3 (`v0.4.11`) and 2.2.4 (`v0.4.12`) from `release/0.4.z`. No upstream change or Konflux source-reference bump is left to do. The latest 2.2.x release is not vulnerable.

**Recommendation:** create **no new remediation tasks for 2.2.x**. Correct Affects Versions to 2.2.0–2.2.2 (Step 3) and record in the summary comment that the fix is available in RHTPA 2.2.3 and later. The engineer still has to confirm this. Before closing out the stream, confirm that `release/0.4.z` HEAD still has quinn-proto >= 0.11.14 (`git -C /home/dev/repos/rhtpa-backend show release/0.4.z:Cargo.lock | grep -A2 'name = "quinn-proto"'`).

### Out-of-scope stream 2.1.x (Case A, preemptive)

Both 2.1.x releases ship quinn-proto 0.11.9. There is no evidence of a fix on `release/0.3.z`. The Step 4 sibling search was not run in this eval, so we assume no 2.1.x CVE Jira exists for CVE-2026-31812. On that assumption, create **preemptive** remediation tasks: an upstream backport plus a downstream propagation, labeled `security-preemptive` and linked to TC-8001 as **Related**. If a 2.1.x sibling CVE Jira does exist, skip task creation and leave 2.1.x to that issue.

- Update quinn-proto dependency to >= 0.11.14 in Cargo.lock
  (`cargo update -p quinn-proto --precise 0.11.14` or later)

  code-level workaround is viable (see upstream changelog)

### Remediation approach (transitive dependency)

**Preferred: bump the direct dependency**
- Identify the direct dependency that pulls in quinn-proto (e.g., quinn / reqwest)
- Bump it to a version whose transitive closure includes quinn-proto >= 0.11.14
  (quinn-proto 0.11.14 is semver-compatible with 0.11.9, so `cargo update -p quinn-proto`
  is expected to suffice without changing Cargo.toml)
- Verify the bump does not introduce breaking API changes

**Fallback: pin the transitive dependency directly**
- `cargo add quinn-proto@0.11.14` to override the transitive resolution
- Document why the direct dep bump was not viable in the PR description
