# Reuse Analysis: TC-9203 -- Add Package License Filter to List Endpoint

## Overview

The task description identifies three Reuse Candidates. All three are used in the implementation plan. No additional reusable code was identified beyond what the task listed. This analysis details how each candidate is reused and why duplication is avoided.

---

## Reuse Candidate 1: `common/src/db/query.rs::apply_filter`

**Source**: `common/src/db/query.rs`

**What it provides**: Handles comma-separated multi-value query parameter parsing and SQL IN clause generation. Given a string like `"MIT,Apache-2.0"`, it splits on commas, trims whitespace, validates non-empty values, and produces a SeaORM condition equivalent to `WHERE column IN ('MIT', 'Apache-2.0')`.

**How it is reused**: Called directly from the package list endpoint handler (`modules/fundamental/src/package/endpoints/list.rs`) to parse the `license` query parameter value. The parsed output (a `Vec<String>` or equivalent filter condition) is passed to the service layer.

**Reuse type**: Direct invocation -- no modification to `apply_filter` is needed. The function's existing interface already supports the exact use case (single and multi-value comma-separated string to SQL IN clause).

**Why reuse instead of new code**: Writing new comma-parsing and IN clause generation logic would duplicate `apply_filter`'s exact functionality. The `common` crate is already a dependency of `modules/fundamental` (it provides `PaginatedResults`, `AppError`, and other shared types), so no new dependency is introduced.

**Dependency check**: `common` is already listed as a dependency in `modules/fundamental/Cargo.toml` (verified by the existing use of `PaginatedResults` from `common::model::paginated` and `AppError` from `common::error` in the package module). No new crate dependency needed.

## Reuse Candidate 2: `modules/fundamental/src/advisory/endpoints/list.rs` (severity filter pattern)

**Source**: `modules/fundamental/src/advisory/endpoints/list.rs`

**What it provides**: A structural pattern for adding an optional filter parameter to a list endpoint. The advisory endpoint's Query struct includes an `Option<String>` field for `severity`, and the handler passes this to the advisory service after processing through `apply_filter`. This is the same architectural pattern needed for the license filter.

**How it is reused**: Used as a structural reference (not direct code import) for:

1. **Query struct pattern**: The advisory endpoint defines a query struct with optional filter fields (e.g., `severity: Option<String>`). The package endpoint's query struct will add `license: Option<String>` following the identical pattern.

2. **Handler flow**: The advisory handler checks if the severity filter is `Some`, calls `apply_filter`, passes the result to the service layer, and returns the paginated response. The package handler will follow the same control flow for the license filter.

3. **Service integration**: The advisory service's `list` method accepts an optional filter parameter and applies it to the SeaORM query. The package service's `list` method will accept an optional `license_filter` parameter using the same pattern.

**Reuse type**: Pattern replication -- the advisory code serves as a template. The actual code is written fresh in the package module but follows the identical structure, naming conventions, and error handling approach.

**Why reuse this pattern**: The advisory severity filter is structurally identical to the needed license filter. Both are:
- Optional query parameters on a list endpoint
- Comma-separated multi-value filters
- Processed by `apply_filter`
- Applied as WHERE IN clauses through the service layer

Following the established pattern ensures consistency across the codebase and makes the code immediately recognizable to developers familiar with the advisory module.

## Reuse Candidate 3: `entity/src/package_license.rs`

**Source**: `entity/src/package_license.rs`

**What it provides**: The SeaORM entity definition for the package-license join table. Maps the database relationship between packages and their declared licenses. Contains the entity struct, column definitions (likely `package_id` and `license` or `spdx_id`), and SeaORM relation definitions that enable type-safe JOINs.

**How it is reused**: Used in the package service's `list` method (`modules/fundamental/src/package/service/mod.rs`) for the JOIN query:

1. **JOIN definition**: `package_license::Entity` is used with SeaORM's `JoinType::InnerJoin` to join the package table to the package_license table on `package.id = package_license.package_id`.

2. **WHERE clause target**: `package_license::Column::License` (or the equivalent column name) is used as the target column for the IN filter condition generated by `apply_filter`.

3. **Relation traversal**: The entity's `Relation` definitions (connecting to `package::Entity`) are used by SeaORM to generate the correct JOIN ON clause automatically, avoiding raw SQL.

**Reuse type**: Direct use of existing entity -- no modification needed. The entity already defines the table mapping and relations required for the filter JOIN.

**Why reuse instead of raw SQL**: Using the SeaORM entity provides type-safe column references, automatic JOIN clause generation from relation definitions, and consistency with the rest of the codebase (which uses SeaORM entities throughout). Writing raw SQL would bypass SeaORM's type system and diverge from the established data access pattern.

**Dependency check**: The `entity` crate is already a dependency of `modules/fundamental` (verified by the existing use of `package::Entity` and other entities in the service layer). No new crate dependency needed.
