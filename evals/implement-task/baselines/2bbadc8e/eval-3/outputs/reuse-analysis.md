## Candidate 1: `common/src/db/query.rs::apply_filter`

**Description from task**: Handles comma-separated multi-value query parameter parsing
and SQL IN clause generation.

**Reuse decision**: Use directly -- no modification needed.

**How it would be reused**:

The `apply_filter` function is the core utility that makes the license filter work
without writing any custom parsing or SQL generation logic. It would be called in
`PackageService::list()` (in `modules/fundamental/src/package/service/mod.rs`) when
the `license` filter parameter is present.

Specifically:
1. The handler extracts `query.license` as an `Option<String>` from the request.
2. When `Some(value)`, the service passes the string to `apply_filter`.
3. `apply_filter` splits on commas, trims whitespace, and generates a
   `column.is_in(values)` SeaORM condition.
4. The condition is added to the query builder.

This avoids writing any custom comma-parsing logic or manual SQL IN clause
construction. The function already handles edge cases (single value, multiple values,
whitespace trimming) that would otherwise need to be re-implemented.

**Dependency check**: `common` is already a dependency of `modules/fundamental`
(it provides `PaginatedResults`, `AppError`, and other shared types). No new
dependency needed -- just an additional import from the existing `common::db::query`
module.

## Candidate 2: `modules/fundamental/src/advisory/endpoints/list.rs`

**Description from task**: The severity filter implementation is structurally identical
to the license filter needed here; follow the same Query struct pattern with an
optional field.

**Reuse decision**: Use as a structural template -- copy the pattern, not the code.

**How it would be reused**:

This file serves as the reference implementation for the entire filter feature. The
advisory list endpoint already implements a query parameter filter (`severity`) using
the exact same architectural pattern needed for the license filter. The implementation
would mirror its structure at two levels:

**Endpoint layer** (`modules/fundamental/src/package/endpoints/list.rs`):
- Add an `Option<String>` field named `license` to the package query parameters
  struct, exactly as the advisory endpoint has a `severity` field in its query struct.
- Both use `#[derive(Deserialize)]` for automatic extraction from URL query parameters.
- Pass the field value through to the service layer.

**Service layer** (`modules/fundamental/src/package/service/mod.rs`):
- Add a `license_filter: Option<String>` parameter to `PackageService::list()`,
  mirroring how `AdvisoryService::list()` accepts a severity filter parameter.
- Apply conditional join and filter using the same pattern: check if filter is
  `Some`, build join, call `apply_filter`, add condition to query.

This is pattern reuse (following an established convention), not code duplication.
The advisory implementation provides the authoritative example of how filters are
structured in this codebase, ensuring the new code is consistent with existing
patterns rather than inventing a different approach.

## Candidate 3: `entity/src/package_license.rs`

**Description from task**: Existing entity for the package-license join table; use
for the JOIN query rather than writing raw SQL.

**Reuse decision**: Use directly -- import and reference in the query builder.

**How it would be reused**:

The `package_license` entity provides the SeaORM model for the join table that
connects packages to their licenses. It would be used in
`PackageService::list()` to build the JOIN clause:

1. Import `entity::package_license` (the entity module) and its `Column` enum.
2. When the license filter is active, add a JOIN from the `package` table to the
   `package_license` table on `package.id = package_license.package_id`.
3. Apply the filter condition on `package_license::Column::License` (or the
   equivalent SPDX identifier column) using the condition generated by
   `apply_filter`.
4. Add `.distinct()` to the query to prevent duplicate packages when a package
   matches multiple license values through the join.

This avoids writing raw SQL joins and keeps the implementation within SeaORM's
type-safe query builder. The entity already defines the column mappings, relations,
and table name -- no schema work or new entity creation required.

**Dependency check**: `entity` is already a dependency of `modules/fundamental`
(it provides `package`, `sbom`, `advisory`, and other entities). The
`package_license` entity is in the same crate -- just an additional import.
