# Reuse Analysis for TC-9203: Add package license filter to list endpoint

## Overview

The task description provides three Reuse Candidates. All three are directly applicable and
should be reused as described. No additional reusable code was identified beyond what the
task lists, though the convention conformance analysis confirms these are the correct
patterns to follow.

---

## Reuse Candidate 1: `common/src/db/query.rs::apply_filter`

**Source**: `common/src/db/query.rs`

**What it provides**: The `apply_filter` function handles comma-separated multi-value query
parameter parsing and SQL `IN` clause generation. It takes a raw string like
`"MIT,Apache-2.0"`, splits it on commas, trims whitespace, and produces a collection
suitable for use with SeaORM's `.is_in()` filter.

**How it will be reused**: Called directly from `PackageService::list()` in
`modules/fundamental/src/package/service/mod.rs`. When the `license` query parameter is
present, the raw string value is passed to `apply_filter` to produce the parsed license
values. These values are then used in a `.filter(package_license::Column::License.is_in(values))`
clause.

**Reuse type**: Direct invocation -- no modification to `apply_filter` is needed. The
function is already a shared utility in the `common` crate, which is a dependency of the
`fundamental` module (verified via the Cargo.toml dependency chain: `modules/fundamental`
depends on `common`).

**Benefit**: Eliminates the need to write custom comma-separated parsing logic. Ensures
consistent behavior with other filter parameters across the API (e.g., the advisory
severity filter uses the same function). Any future improvements to `apply_filter`
(e.g., trimming, deduplication, escaping) automatically apply to the license filter.

**Decision rationale**: The `common` crate is already a dependency of the `fundamental`
module, so no new dependency is introduced. This follows the skill's "reuse over
duplication" guidance (Step 6): when the dependency already exists, use the existing
function rather than duplicating it.

## Reuse Candidate 2: `modules/fundamental/src/advisory/endpoints/list.rs`

**Source**: `modules/fundamental/src/advisory/endpoints/list.rs`

**What it provides**: The advisory list endpoint implements a `severity` query parameter
filter using a pattern that is structurally identical to the license filter needed here.
Specifically:
- A `Query` struct with an optional `severity: Option<String>` field annotated with
  `#[serde(default)]`
- The handler extracts the query parameter via Axum's `Query<T>` extractor
- The parameter value is passed to `AdvisoryService::list()` which uses `apply_filter`
  to process it

**How it will be reused**: The advisory endpoint serves as a structural template -- its
`Query` struct pattern, parameter extraction, and service-layer integration will be
replicated in the package endpoint. Specifically:

1. **Query struct pattern**: add `license: Option<String>` to the package endpoint's
   `Query` struct, following the same `#[serde(default)]` annotation pattern used for
   `severity` in the advisory endpoint.

2. **Handler pattern**: pass the extracted `license` value to `PackageService::list()`
   in the same way the advisory handler passes `severity` to `AdvisoryService::list()`.

3. **Service integration pattern**: in `PackageService::list()`, conditionally apply the
   license filter using the same `if let Some(filter) = license { apply_filter(...) }`
   pattern used in `AdvisoryService::list()` for severity.

**Reuse type**: Structural template (pattern replication) -- the advisory code is not
called or imported, but its design pattern is followed exactly. This is the intended use
described in the task's Implementation Notes.

**Benefit**: Ensures the license filter implementation is consistent with existing filter
patterns in the codebase. Reduces implementation risk by following a proven, tested
pattern. Makes the codebase more maintainable since all filter parameters follow the same
structural approach.

## Reuse Candidate 3: `entity/src/package_license.rs`

**Source**: `entity/src/package_license.rs`

**What it provides**: The SeaORM entity definition for the package-license join table. This
entity maps packages to their declared licenses and includes:
- Column definitions (at minimum `package_id` and a license identifier column)
- SeaORM relation definitions linking to the `package` entity
- The `Model`, `ActiveModel`, `Entity`, and `Column` types generated by SeaORM derive macros

**How it will be reused**: Used in `PackageService::list()` to construct the JOIN query
for license filtering. Instead of writing raw SQL for the join, the implementation uses
the entity's relation definitions and column types:

```rust
// Join through the existing entity relation
query = query
    .join(JoinType::InnerJoin, package_license::Relation::Package.def().rev())
    .filter(package_license::Column::License.is_in(license_values));
```

This leverages SeaORM's type-safe query builder with the existing entity definition,
ensuring:
- Column names are correct (defined once in the entity, not duplicated as strings)
- Relations are correct (defined once in the entity's `Relation` enum)
- Query is type-checked at compile time

**Reuse type**: Direct usage -- the entity is imported and used in query construction.
No modifications to the entity file are needed.

**Benefit**: Avoids raw SQL strings for the join, which would be fragile and bypass
SeaORM's type checking. If the table schema changes (e.g., column renames), the entity
definition is the single source of truth and the compiler will flag any mismatches.
Follows the established convention in the codebase where all database queries use SeaORM
entities rather than raw SQL.

## Additional Reuse Opportunities Identified

### `common/src/model/paginated.rs` (PaginatedResults)

The existing `PaginatedResults<T>` wrapper is already used by the package list endpoint
and will continue to be used without modification. The response shape does not change --
this is an existing reuse that requires no action, but is noted for completeness.

### `common/src/error.rs` (AppError)

The `AppError` enum with `IntoResponse` implementation will be used for the `400 Bad
Request` response when an invalid license value is provided. This follows the established
error handling convention across all endpoints. No modification to `AppError` is needed
unless it lacks a variant suitable for validation errors (in which case an existing variant
like `BadRequest` or `InvalidInput` would be used).
