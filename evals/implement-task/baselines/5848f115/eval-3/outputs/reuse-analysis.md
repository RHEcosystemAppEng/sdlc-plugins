# Reuse Analysis: TC-9203 -- Add package license filter to list endpoint

This document details the three Reuse Candidates identified in the task description
and how each is used in the implementation, in accordance with constraint 5.4 (reuse
existing code rather than writing new logic that duplicates it).

## Reuse Candidate 1: `common/src/db/query.rs::apply_filter`

**What it provides**: The `apply_filter` function handles comma-separated multi-value
query parameter parsing and SQL `IN` clause generation. Given a raw query parameter
string like `"MIT,Apache-2.0"`, it splits on commas, trims whitespace, and produces
the appropriate filter condition for the database query.

**How it is reused**: This function is called directly in both modified files to handle
license filter parsing. In `modules/fundamental/src/package/endpoints/list.rs`, the raw
`license` query parameter string is passed to `apply_filter` to produce the parsed
filter values. In `modules/fundamental/src/package/service/mod.rs`, `apply_filter` is
used to apply the parsed filter to the SeaORM query builder, generating an SQL `IN`
clause against the license column of the `package_license` join table.

**Why reuse instead of new code**: Writing custom comma-splitting logic (e.g.,
`.split(',').map(|s| s.trim()).collect()`) would duplicate functionality that
`apply_filter` already provides, tested and used across other modules. Using
`apply_filter` ensures consistent parsing behavior across all filter parameters in
the API (advisory severity, package license, etc.) and avoids introducing a parallel
code path that could diverge in edge-case handling (empty segments, whitespace,
special characters).

**No new utility functions are created** that duplicate `apply_filter`'s functionality.

## Reuse Candidate 2: `modules/fundamental/src/advisory/endpoints/list.rs`

**What it provides**: The advisory list endpoint implements an optional `severity` query
parameter using a Query struct pattern with an optional field. The handler extracts the
parameter, passes it to the service layer, and the service applies the filter using
`apply_filter`. This is structurally identical to the license filter needed for the
package endpoint.

**How it is reused**: This file serves as the structural guide for all changes. The
implementation follows the same pattern:

1. **Query struct**: Add an `Option<String>` field for `license` to the package
   endpoint's Query struct, mirroring how `severity` is declared as an optional field
   in the advisory Query struct.
2. **Handler flow**: Extract the license parameter from the query and pass it to the
   service method, following the same control flow as the advisory handler passes
   `severity` to `AdvisoryService::list()`.
3. **Service integration**: The service method accepts the optional filter and
   conditionally applies it, following the same conditional-filter pattern used in
   the advisory service.

**Why reuse this pattern**: The advisory filter pattern is a proven, reviewed
implementation that already exists in the same module family (`modules/fundamental`).
Following it ensures consistency across endpoints, makes the codebase predictable for
reviewers and maintainers, and avoids inventing a novel approach when an established
one exists.

## Reuse Candidate 3: `entity/src/package_license.rs`

**What it provides**: The existing SeaORM entity definition for the `package_license`
join table, which maps packages to their declared licenses. This entity defines the
table schema, column mappings, and relationships needed to query the package-license
association.

**How it is reused**: In `modules/fundamental/src/package/service/mod.rs`, when the
license filter is present, the query builder JOINs with the `package_license` entity
to filter packages by their associated license identifiers. The entity's column
definitions (e.g., `package_license::Column::License`) are used in the filter
condition generated by `apply_filter`.

**Why reuse instead of alternatives**:
- Writing raw SQL (`JOIN package_license ON ...`) bypasses SeaORM's type safety and
  query building, making the code inconsistent with the rest of the codebase which
  uses SeaORM entities throughout.
- Creating a new entity for the same table would duplicate the schema definition
  already in `entity/src/package_license.rs` and risk divergence if the table schema
  changes.
- The existing entity is already a dependency of `modules/fundamental` (via the
  `entity` crate in `Cargo.toml`), so no new cross-package dependency is introduced.

## Summary

All three Reuse Candidates are used directly in the implementation. No new utility
functions, entity definitions, or parsing logic are created that would duplicate the
functionality provided by these existing components. The implementation follows
constraint 5.4 by reusing existing code paths rather than writing parallel
implementations.
